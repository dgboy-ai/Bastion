# Bastion: 4-Memory Framework Integration Plan

## The Presentation's Key Insight

The presentation identifies **4 distinct memory types** that agents need simultaneously:
1. **In-context** (working memory) — current session state
2. **Episodic** (past interactions) — conversation history
3. **Semantic** (facts/documents) — knowledge base
4. **Procedural** (rules/guardrails) — behavioral constraints

Each has a specific failure mode:
- In-context: "It forgets what you told it" (context truncation at Turn 140)
- Episodic: "It gets slower as it remembers more" (p99 latency crosses timeout)
- Semantic: "It answers wrong, with full confidence" (stale content, compliance violation)
- Procedural: "It drifts off procedure midtask" (drift begins at Turn 40)

## The Master Design Matrix (From Presentation)

The presentation provides a complete architecture for each memory type:

### 1. In-Context Design
- **Strategy:** Bound the window; do not let it grow infinitely
- **Implementation:** Sliding window with priority-ranked truncation
- **Optimization:** Summarize evicted turns to keep core ideas
- **Evaluation:** Constraint-recall tests at turns 50, 100, 200

### 2. Episodic Design
- **Strategy:** Treat latency as a strict budget
- **Implementation:** Tiered vector store with recency decay
- **Optimization:** Pre-filter by relevance before ANN search
- **Evaluation:** Track p99 latency against corpus size

### 3. Semantic Design
- **Strategy:** Treat data freshness as first-class SLA
- **Implementation:** Event-driven reindexing
- **Optimization:** Version documents, force confidence scores
- **Evaluation:** Staleness audits comparing DB vs source-of-truth

### 4. Procedural Design
- **Strategy:** Encode rules as enforced state, not prose
- **Implementation:** Finite-state checks outside prompt
- **Optimization:** Re-assert critical constraints every N turns
- **Evaluation:** Long-session drift tests past Turn 40

## Key Takeaway

The presentation validates our architecture but reveals we're missing the **management layer** for each memory type. We have the storage (CockroachDB), the search (C-SPANN), and the security (hash chains). What we need is the **orchestration** that binds them together as 4 distinct systems.

This is exactly what the hackathon judges want to see: not just a memory store, but a **memory operating system** that understands the 4 types and manages each appropriately.
